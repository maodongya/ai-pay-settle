## 1. 监控结论（一句话）

**分阶段短事务显著缓解连接池耗尽（Hikari 活跃 11~14/28，无 30s 超时风暴），MQ 积压可在约 4.5 分钟内清空；但真实清算成功率极低（≈1.6 单/秒），主瓶颈是历史脏消息幂等跳过 + `finalizeSuccess` 跨事务查不到任务 + 偶发死锁，而非连接池。**

## 7. 性能瓶颈排序（为后续优化）

### P0 — 数据正确性 / 无效消费（影响有效 TPS）

1. **`finalizeSuccess` 跨事务 `findByBillNo` 失败（`No value present`，日志 238 次）**  
   - 位置：`ClearanceTaskTxSupport.finalizeSuccess:111`  
   - 原因推测：`claim` 与 `finalize` 为独立 `@DSTransactional`，`findByBillNo` 依赖 `bill_route` 路由；高并发或路由未就绪时查不到 RUNNING 任务。  
   - **优化**：`claim` 返回 `ClearanceTaskEntity` 或在 `bill` 上携带 `merchantId/shardId`，`finalize` 用 `merchantId` 精确路由，避免二次 `bill_route` 查询；或将 finalize 与 claim 合并为同一短事务。

2. **历史脏 MQ（~1.4 万条）导致海量 skip**  
   - 大量消息对应任务已 DEAD/SUCCESS，消费线程空转。  
   - **优化**：压测/drain 前 `resetOffsetByTime` + 清理 DEAD 任务；或消费端按 `billNo` 本地 Bloom 过滤已终态任务。

3. **MySQL 死锁（64 次）**  
   - 集中在 `claimAndMarkClearing` / `clearance_task` + `trade_bill` 并发更新。  
   - **优化**：统一锁顺序（先 task 后 bill）、`claim` 使用更窄索引更新、死锁重试。

### P1 — 单条路径耗时（影响理论上限）

4. **`fee_split` 阶段 100ms+ 为主耗时**  
   - 内含：计费规则查询（Redis 已缓存）、`splitService.generateSplitDetail` 多表写入。  
   - **优化**：延续 PR-A 批量写入到 voucher/outbox；计费结果缓存；减少 `finalize` 内二次 `findByBillNo`。

5. **`finalize` 二次查 task + 两次 save**  
   - **优化**：`claim` 阶段缓存 task 主键，`finalize` 改 `updateStatusByBillNo` 单 SQL。

### P2 — 吞吐调优（连接池已非瓶颈）

6. **calc-thread-max=12 未饱和**（Hikari 仅用一半）  
   - 可在修复 P0 后再评估升至 16；当前提升线程数收益有限。

7. **DEAD 任务 6,077 条**  
   - 需人工/脚本修复数据或隔离，避免 Retry Job 与 MQ 重复消费。

## 8. 建议优化路线（PR-C / PR-D）

| 优先级 | PR | 内容 | 预期收益 |
|--------|-----|------|----------|
| P0 | PR-C1 | `finalize` 携带 merchantId 路由 / 合并 claim 上下文 | 消除 No value present，有效 TPS ×5~10 |
| P0 | PR-C2 | drain 前 MQ offset 重置 + DEAD 任务隔离 | 减少 90%+ skip 空转 |
| P1 | PR-C3 | `updateStatusByBillNo` 替代 find+save | finalize −30ms |
| P1 | PR-D1 | split/outbox 批量写入延伸 | fee_split −20~40% |
| P2 | PR-D2 | 死锁重试 + 锁顺序规范 | 稳定性 |
| P2 | PR-D3 | calc-thread 12→16（P0 修复后压测验证） | 边际提升 |
