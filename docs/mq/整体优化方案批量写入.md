# MQ 消费 / 清算整体优化方案（批量写入 + 连接池对齐）

> 版本：V1.0 | 日期：2026-07-16  
> 背景：清库后 30 TPS × 10 分钟 MQ 压测发送 18000 全成功，但 `bill_route` / 清算落库严重滞后，应用日志出现大量 `Connection is closed` / consume failed。  
> 关联：[数据库连接池优化.md](../db/数据库连接池优化.md)、[mq性能优化实施方案.md](./mq性能优化实施方案.md)、[mq多线程.md](./mq多线程.md)

---

## 1. 结论摘要

| 判断 | 说明 |
|------|------|
| 主因 | 清算单消息 SQL 多（~15–25）、事务持连长；分片三层池中 **proxy 池偏紧** |
| 假批量 | `MapperHelper.saveAll` 为 for-loop 单插；JDBC 已开 `rewriteBatchedStatements` 但未生效 |
| 真批量收益 | 单消息内 `split_detail` / `account_voucher` 多值 INSERT，预计清算 RT **-25%～40%** |
| 跨消息 Batch Listener | 分片 + 状态机复杂，**不作为首期**；Settle 禁止跨商户批更新余额 |
| 调优顺序 | **降 \(RT_{tx}\)** → **池对齐线程** → 再小幅加线程 / 多实例 |

## 2. 现状诊断

### 2.1 链路

```
trade_pay → Access(落单+建任务) → clearance_task → Calc(计费+分账+outbox)
       → OutboxJob → settle_amount(ORDERLY) → 入账
```

| 阶段 | 线程(sharding+mq) | 单消息量级 | 事务 |
|------|-------------------|-----------|------|
| Access | 8 | ~5–7 SQL | `@DSTransactional` 仅 persist |
| Calc（最热） | 8 | **~15–25 SQL** | 整段 `executeTask` 大事务 |
| Settle | 8 ORDERLY | ~4–6 SQL + Redis 商户锁 | 短事务 |

### 2.2 连接模型

```
消费线程 ──借──► dynamic 外层池
                    ├─ pay_config (16)     ← bill_route / 主数据
                    └─ SS 代理池           ← 易先打满
                         └─ ds_0..3        ← 业务分片物理连接
```

有效清算 TPS 粗估：

\[
TPS_{\text{calc}} \approx \frac{N_{\text{calc\_threads}} \times U_{\text{conn}}}{RT_{\text{tx}}}
\]

RT 被连接等待拉到秒级时，落库吞吐会掉到个位数，与「发 30、落库远低于发送」一致。

### 2.3 批量插入评估

| 类型 | 表 | 评估 |
|------|-----|------|
| **单消息内真批量（P0）** | `split_detail`、`account_voucher` | 同 `merchantId` → 同分片，改造小、ROI 高 |
| 单插表 | `trade_bill` / `clearance_task` / `outbox` / `fee_calc_result` | 每单 1 行，收益有限 |
| 跨消息 Batch Listener | Access 按 shard 微批 | 可选 P2；Calc/Settle 不适合整批一事务 |

## 3. 分阶段方案

### 阶段 P0（已实现本文件 PR-A / PR-B）

#### PR-A：真批量写入

- Mapper：`insertBatch(List)` 多值 `INSERT ... VALUES (...),(...)`
- Repository：`saveAll` 对无主键列表走 `insertBatch`；有主键仍逐条 update
- `createTime`：业务侧已赋值；Repository 对 null 补当前时间（自定义 SQL 不走 MetaObjectHandler）
- 约束：同一批必须同 `merchantId`（分片键），由清算路径天然保证

#### PR-B：池对齐消费线程

消费并发约 `8+8+8+4≈28`，原 proxy=20 成为闸门。

| 池 | 优化前 | 优化后 | 说明 |
|----|--------|--------|------|
| pay_config | 16 | 16 | 不变 |
| pay-data-shard-proxy | 20 | **28** | ≈ 消费线程合计 |
| ds_0..3 各 | 12 | **14** | 内层略抬，总物理 **16+56=72** |
| dynamic / spring fallback | 20 | **28** | 与 proxy 对齐 |

约束：

\[
N_{\text{access}}+N_{\text{calc}}+N_{\text{settle}} \le 0.7 \times \text{proxyPool}
\]

当前 24 ≤ 0.7×28，留余量给 Outbox/Job。

### 阶段 P1（后续）

1. `executeTask` 事务拆段（claim / fee+split / success）缩短持连  
2. Outbox：缩短间隔 / 加大 batch，或 afterCommit 直发 + Job 兜底  
3. 池稳定后线程阶梯：8→12，每次只改一个变量压测  

### 阶段 P2（可选）

1. 多实例水平扩容（每实例池预算按实例数下调）  
2. Access 按 shard 微批落单（复杂，排在 P0/P1 后）  

---

## 4. 设计约束

1. 批写必须同 `merchantId` / 同 shard  
2. Settle 保持 ORDERLY + `settle:lock`，禁止跨商户批改余额  
3. 线程与池联动修改；保留 Hikari leak detection  
4. 幂等：`bill_route` / `claimTask` / `existsByBillNo` / `account_flow`  
5. 一次只改一个变量做对比压测  

---

## 5. 验收标准

| 指标 | 基线（30×10min） | P0 目标 |
|------|------------------|---------|
| 发送成功率 | 100% | 保持 |
| `bill_route` vs 发送 | 严重滞后 | drain 后接近 1:1，稳态 Lag &lt; 1000 |
| 连接超时 / broken | 大量 | 接近 0 |
| 清算单笔 SQL（split+voucher） | N 次单插 | **各 1 次**多值 INSERT |

压测：

```bash
# 清库 + 种子后
TPS=30 DURATION=600 bash ./scripts/run-loadtest-003.sh
# 观察 Hikari pending / acquire、Topic Lag、bill_route 增长斜率
```
