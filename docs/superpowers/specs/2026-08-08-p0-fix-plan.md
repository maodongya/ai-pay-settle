## P0-1 回调一致性

### 现状（本分支）

入口：`SettleAccountServiceImpl.handlePaymentCallback` → `SettleAccountTxSupport.applyPaymentCallback`。

```text
同一 @Transactional：
  1) deductFrozen / unfreeze（AccountOperator，内含 Redis 锁）
  2) updatePaymentResult(PAYING → SUCCESS/FAILED)  CAS
  3) 若 updated==0：直接 return，不抛异常
  4) 更新提现申请状态
```

告警在事务外（失败时），方向正确。

### 根因

1. **CAS 未命中仍提交账户变动**  
   `updatePaymentResult` 返回 0 时方法正常返回 → 事务提交 → 可能出现「余额已扣/已解冻，订单仍为 PAYING」或与并发回调交错。  
   幂等流水可缓解部分重复扣款，但**订单状态与资金状态仍可能不一致**。

2. **渠道在提现事务内提交**  
   `applyWithdraw` 仍 `@Transactional`，末尾 `paymentChannel.submitAsync`。事务回滚时渠道可能已受理（或持连发 IO）。

3. **AccountOperator 事务内持 Redis 锁**  
   锁跨度被外层回调/提现事务拉长；`NoOp` 降级时多实例无串行。

4. **（未来 ACCOUNT_ONLY）**  
   若合并账务分支的「先 Dubbo 后本地」，裂脑风险更大，需单独补偿编排。本分支先按 LOCAL 闭环。

### 优化方案（推荐）

**目标时序：**

```text
校验订单存在且非终态（事务外读）
  → 短事务唯一边界：
       CAS 更新订单 PAYING→目标态
       若 CAS 失败：抛业务幂等/冲突，整事务回滚（不做资金写）
       若 CAS 成功：再做 deduct/unfreeze（同事务）
       更新提现申请
  → 事务外：失败告警
```

要点：

| 步骤 | 做法 |
|------|------|
| 先 CAS 后资金 | 只有抢到状态迁移权才动余额；CAS 失败直接 return（幂等）或抛错回滚 |
| 去掉 Operator 嵌套事务 | Operator 去 `@Transactional`，只留 TxSupport 一层 |
| 锁外置或删除 | 优先靠 CAS + 流水唯一约束；若保留 Redis 锁，必须包在「整段短事务」之外 |
| 渠道 afterCommit | `applyWithdraw` 拆编排：短事务落单+冻结 → `AfterCommit`/`事务返回后` 再 `submitAsync` |

**验收：**

- 并发双回调：仅一笔资金变动，订单终态唯一。  
- 提现事务故意失败：Mock 渠道零调用。  
- 单测：`updatePaymentResult=0` 时余额不变。

## P0-2 Watchdog 原子修复

### 现状

`ClearanceRetryJob.watchdog`：

- 扫描 `RUNNING` 且 `update_time` 超时的任务  
- **仅** `task.status = FAILED` + `save`  
- **不**回写 `trade_bill`（可能仍为 CLEARING）  
- **不**重置为可重试语义清晰的状态机（与 `markFailure` 不一致）

### 根因

看门狗绕过了 `ClearanceTaskTxSupport.markFailure`，造成 task/bill 状态机分叉；后续 `retryFailed` 可能重跑，但账单 CLEARING 会干扰 claim/快速跳过逻辑。

### 优化方案（推荐）

新增短事务 API，例如：

```text
ClearanceTaskTxSupport.watchdogFail(billNo, merchantId):
  @DSTransactional
  - CAS：task RUNNING → FAILED（带 error_msg、next_retry_time、retry_count+1 或沿用 markFailed SQL）
  - CAS：bill CLEARING → FAILED（仅当仍为 CLEARING）
  - 若达 DEAD 阈值：返回 enteredDead，由 Job 事务外开单告警
```

Job 改为：

```text
for each stale:
  outcome = txSupport.watchdogFail(...)
  if outcome.enteredDead: openClearanceDead + alert
```

**不要**在 Job 里直接 `entity.status=...; save`。

**验收：**

- 人为卡住 RUNNING+CLEARING 超 30 分钟后，task 与 bill 同为 FAILED。  
- 可被 `retryFailed` 正常拉起。  
- 已 CLEARED/SUCCESS 的不被 Watchdog 误伤（CAS 条件）。

## P0-3 接入补偿

### 现状

`BillAccessServiceImpl.submitBill`：

```text
persistNewBill（短事务：trade_bill + bill_route）
  → createTask（事务外）
  → triggerClearance（MQ 或 sync）
```

已有 `BillRouteCompensateJob`：只补 **缺失的 bill_route**，不补 **缺失的 clearance_task**，也不重发 MQ。

### 故障模式

| 场景 | 结果 |
|------|------|
| persist 成功，createTask 失败 | PENDING 账单无任务 |
| createTask 成功，MQ 发送失败 | 有任务 PENDING，无消息（可靠重试 Job，但依赖任务存在） |
| 仅有账单无 route | 路由补偿可修；仍可能无任务 |

### 优化方案（推荐组合）

**方案甲（最小闭环，优先）：补偿 Job**

新增 `ClearanceTaskCompensateJob`（或扩展现有 access 补偿）：

```text
扫描：status=PENDING 的 trade_bill（按 shard，限流批量）
  若无 clearance_task → createTask
  若任务 PENDING 且 MQ 模式 → 再次 publish（需发布幂等/有序键）
  指标：compensated_task / republish
```

**方案乙（结构更优，可跟进）：Outbox 触发**

```text
persistNewBill 同事务写入 clearance_trigger_outbox
  afterCommit / OutboxJob 负责 createTask + publish
```

一致性更强，改动面大于甲。P0 建议先甲后乙。

**接入侧小改（可选）：**

`createTask` 失败时打 Error 指标并抛给上游可重试（HTTP 5xx / MQ 重试），避免静默 ACK；与补偿 Job 双保险。

**验收：**

- 注入「只落账单不建任务」后，补偿 Job 在一个周期内建齐任务并触发清算。  
- 重复补偿幂等（createTask 已存在则跳过）。

## P0-4 限流 / 锁生产策略

### 现状

| 组件 | 行为 |
|------|------|
| `LayerTpsRateLimiter` | **单 JVM** 串行令牌 + `park` 阻塞 |
| `@DbRateLimit` | 拦 DB 热路径，阻塞 MQ/HTTP 工作线程 |
| `RedisDistributedLockImpl` | SET NX；**无**「事务内禁止加锁」门禁 |
| `NoOpDistributedLock` | `payment.redis.enabled=false` 时**恒成功** |
| `AccountOperator` | **事务内** tryLock + afterCompletion 解锁 |

### 根因

1. 多实例下本地 TPS×N 叠加，击穿 DB。  
2. 阻塞式限流在 MQ 消费线程上放大积压。  
3. NoOp 锁让「以为有锁」变成无锁。  
4. 锁与事务耦合：持锁时间 ≈ 外层事务，吞吐差且易与 sleep 抢锁叠连接占用。

### 优化方案

#### 4.1 锁（与 P0-1 一并做）

1. **生产默认** `payment.redis.enabled=true`；启动校验：多实例部署禁止 NoOp。  
2. 可选：`payment.redis.lock.fail-closed=true` 时，Redis 不可用直接拒绝写路径（优于静默 NoOp）。  
3. `AccountOperator`：去掉事务内锁（见 P0-1）；并发靠 CAS + 流水 UK。  
4. `RedisDistributedLockImpl.tryLock`：若 `TransactionSynchronizationManager.isActualTransactionActive()` 则抛错（门禁）。

#### 4.2 限流

**短期（P0）：**

```yaml
pay:
  db-rate-limit:
    enabled: true
    # 按实例数均分，文档写清：总 TPS ≈ 配置 × 实例数
    access-tps: 10      # 例：3 实例 ≈ 30
    calc-tps: 10
    settlement-tps: 10
    mode: block         # 现状
```

启动日志打印「有效集群近似上限」，避免误配。

**中期（P0 尾声 / P1）：**

- `mode: reject`：拿不到令牌抛 429 / 可重试异常，**不 park** 消费线程。  
- Redis 令牌桶（或 Redisson）实现跨实例总 TPS。  
- 指标：`db_rate_limit_wait_seconds` / `db_rate_limit_rejected_total`。

### 验收

- 2 实例压测：DB QPS 不超过约定总上限（Redis 限流）或不超过「单机配置×实例数」的文档预期（短期）。  
- Redis 关闭 + fail-closed：写路径失败而非双开。  
- 静态检查：无「@Transactional 方法内 tryLock」。

## 明确不做（本 P0）

- 不上真实银行渠道、不做 ERP。  
- 不在本阶段上 `mqPercent` 灰度与多主体 CLEARANCE_POST。  
- 不把限流一次做成完整集群调度平台；先 fail-safe 与可观测。

## 风险与回滚

| 改动 | 风险 | 回滚 |
|------|------|------|
| 回调先 CAS | 极端并发下成功回调需重试一次 | 开关切回旧顺序（不推荐长期） |
| Watchdog 回写账单 | 误伤 CLEARING | CAS 期望态；灰度超时阈值 |
| 补偿发 MQ | 重复消息 | 消费/claim 幂等已具备 |
| reject 限流 | 瞬时 429 增多 | mode 切回 block |
