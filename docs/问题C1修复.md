# 问题 C1 修复

| 项 | 内容 |
|----|------|
| 编号 | C1 / PR-C1（见 `docs/mq/整体优化方案2.md`） |
| 主题 | `finalizeSuccess` 跨事务 `findByBillNo` 失败（`No value present`） |
| 模块 | `pay-calc`（`ClearanceTaskTxSupport` / `ClearanceTaskServiceImpl`） |
| 原则 | 短事务保留；跨阶段用上下文传分片键；禁止二次弱路由 |
| 相关 | PR-C2 脏 MQ/DEAD 隔离；PR-C3 单 SQL 替代 find+save |

---

## 1. 问题解释

### 1.1 现象

压测（方案 2，短事务落地后）观察到：

- MQ 侧消化可达约 **53 msg/s**（含大量 skip）
- **真实清算成功仅约 1.6–2 单/s**
- 日志大量：`finalizeSuccess` → `findByBillNo` → **`No value present`**（当时约 238 次）

连接池已非主瓶颈；有效吞吐被「finalize 查不到任务」与脏消息 skip 共同打穿。

### 1.2 问题版本时序

```text
TX1  claimAndMarkClearing(billNo[, merchantId])
       claim  PENDING → RUNNING
       bill   PENDING → CLEARING
       返回 bill（或仅 billNo）—— 未稳定携带分片键给后续阶段

（事务外）loadRelation / fee_split …

TX2  finalizeSuccess(billNo)
       task = clearanceTaskRepository.findByBillNo(billNo)  ← 依赖 bill_route 二次路由
       .orElseThrow()                                       ← No value present
       再改 task SUCCESS + bill CLEARED
```

### 1.3 根因

| 点 | 说明 |
|----|------|
| 跨事务丢上下文 | claim 与 finalize 是两个独立 `@DSTransactional`，finalize 不再持有 claim 时的 `merchantId` / 分片信息 |
| 二次路由脆弱 | `findByBillNo` 依赖 `bill_route`；接入同事务路由对 config 尚未可见、路由缺失、分片抖动时都会查空 |
| 失败语义过猛 | Optional 空直接抛错 → 任务可能已 RUNNING、账单 CLEARING，再进 fail/重试，正确性错误吞噬有效 TPS |

**一句话：** 不是算力不够，而是 finalize 用错了路由键（弱 `billNo` 路由代替强 `merchantId` 分片键）。

### 1.4 影响

- 本可成功的清算被记为 fail，触发重试 / DEAD / 告警噪音
- 有效清算 TPS 远低于 MQ 消费 TPS（方案 2：有效 ≈ MQ 的数个百分点）
- 与 C2（历史脏 MQ 海量 skip）叠加时，监控上表现为「消费很快、成功很少」

---

## 2. 优化目标

1. **消除** finalize 路径上的 `findByBillNo` + `No value present`
2. finalize / fail **一律用 claim 带回的 `merchantId` 做精确 CAS**
3. **保持** claim / fee_split / finalize 分阶段短事务（不合并成长事务）
4. CAS 不命中时抛**明确状态不匹配**异常，而非 Optional 空

非目标：不在本问题内做脏 MQ offset 重置（属 C2）；不把 fee+finalize 并回单事务。

---

## 3. 推荐方案

### 3.1 目标时序

```text
TX1  claimAndMarkClearing(billNo, merchantId)
       → 返回 ClearanceClaimContext { bill, merchantId }

（事务外）计费 + 分账

TX2  finalizeSuccess(ctx)
       UPDATE trade_bill
         SET status = CLEARED
         WHERE bill_no=? AND merchant_id=? AND status=CLEARING
       UPDATE clearance_task
         SET status = SUCCESS
         WHERE bill_no=? AND merchant_id=? AND status=RUNNING
       （updated==0 → IllegalStateException: status mismatch）
```

失败路径同源：

```text
markFailure(ctx, e) / watchdogFail(billNo, merchantId)
  → markFailed(RUNNING→FAILED/DEAD) + bill CLEARING→FAILED
  （均带 merchantId，禁止 findByBillNo）
```

### 3.2 设计要点

| 步骤 | 做法 |
|------|------|
| 引入上下文 | `ClearanceClaimContext(TradeBillEntity bill, Long merchantId)`；claim 成功后贯穿 `executeTask` |
| finalize 精确更新 | `updateStatusByBillNoAndMerchantId` + `markSuccess(..., merchantId, ...)`；禁止 find+改内存+save |
| fail / watchdog 同源 | 失败与看门狗同样携带 `merchantId`，避免 RUNNING/CLEARING 分叉 |
| MQ 载荷带 merchantId | 消费端优先用消息内 merchantId；`resolveMerchantId` 仅作兜底（task 表 → bill_route） |
| 明确失败语义 | CAS `updated==0` 抛 `status mismatch`，便于监控与幂等区分 |

### 3.3 方案对比（为何不选其它）

| 方案 | 评价 |
|------|------|
| **A. Claim 上下文 + merchantId CAS（推荐）** | 最小改动，保留短事务，根因对齐 |
| B. claim+fee+finalize 合并单事务 | 持连过长，易打回连接池问题 |
| C. finalize 加重试 / 睡后再 findByBillNo | 掩盖路由问题，高并发仍失败 |
| D. 仅加强 bill_route 可见性 | 治标；跨库延迟与缺失场景仍在 |

### 3.4 涉及文件（落地时）

| 文件 | 职责 |
|------|------|
| `pay-calc/.../ClearanceClaimContext.java` | claim 返回值：bill + merchantId |
| `pay-calc/.../ClearanceTaskTxSupport.java` | claim / finalize / fail 短事务 API |
| `pay-calc/.../ClearanceTaskServiceImpl.java` | 编排：持有 ctx，finalize/fail 传 ctx |
| `pay-domain/.../ClearanceTaskRepository` | `markSuccess` / `markFailed` 带 merchantId |
| `pay-domain/.../TradeBillRepository` | `updateStatusByBillNoAndMerchantId` |

## 4. 实施切片

| 步骤 | 内容 | 验收点 |
|------|------|--------|
| C1-a | 新增 `ClearanceClaimContext`；`claimAndMarkClearing` 返回该上下文 | 编译通过；claim 必带 merchantId |
| C1-b | `finalizeSuccess(ClearanceClaimContext)` 改为 merchantId 双 CAS | 路径无 `findByBillNo` |
| C1-c | `markFailure` / watchdog 同源 merchantId | 失败不依赖 bill_route |
| C1-d | 单测：无 bill_route 桩时 finalize 仍成功；CAS miss 抛明确异常 | 单测绿 |
| C1-e | 压测对比 | 见第 5 节 |

建议提交粒度：C1-a~c 可一个 commit；C1-d 测试；C1-e 压测报告附录。

## 5. 验收标准

| 项 | 通过条件 |
|----|----------|
| 日志 | 压测窗口 `No value present`（finalize 路径）≈ 0 |
| 行为 | finalize 失败仅为「状态 CAS 不匹配」（真并发 / 真脏数据） |
| 代码静态 | `finalizeSuccess` / `markFailure` 主路径无 `findByBillNo` |
| 吞吐 | 有效清算 TPS 相对修复前明显上升（需与 C2 脏消息治理一并解读；文档曾估正确性修复后有数量级提升空间） |
| 回归 | claim 抢占失败仍幂等 ACK；终态 SUCCESS/DEAD 快速 skip 仍有效 |

## 6. 风险与回滚

| 风险 | 缓解 |
|------|------|
| 调用方未传 merchantId | MQ 载荷强制带；本地 sync 路径从接入透传；resolve 兜底顺序：hint → task 表 → bill_route |
| CAS miss 增多被误判为回归 | 指标区分 `status_mismatch` vs `route_miss`；后者应消失 |
| 与旧消费者不兼容 | 旧消息无 merchantId 时走 resolve 兜底，观察期后可告警 |

回滚：恢复 finalize 内 `findByBillNo` 版本（不推荐长期保留）；或特性开关切回旧实现（若曾加开关）。
